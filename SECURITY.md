# Секреты и локальная настройка

Настоящий `.env` хранится только локально и исключён из Git. В репозитории допустим только `.env.example` с пустыми значениями. Новый участник копирует шаблон в `.env` и заполняет его собственными действующими данными. Не отправляйте секреты в чат, issues, README или screenshots.

## Если секрет уже попал на GitHub

1. Немедленно отозвать опубликованный OpenAI API key в [настройках ключей](https://platform.openai.com/api-keys), создать замену и проверить расходы/использование. Если ключ выдан организаторами, запросить отзыв и замену у владельца проекта.
2. Сменить опубликованный пароль EKT у владельца аккаунта или через доступный механизм сброса пароля. По возможности завершить старые сеансы. Если этот пароль использовался где-либо ещё, заменить его и там.
3. Внести новые значения только в локальные `.env` и хранилища секретов серверов/деплоя; перезапустить соответствующий backend. Новые значения не коммитить.
4. Проверить, что `.env` больше не отслеживается. Наличие файла в `.gitignore` само по себе не удаляет ранее закоммиченный файл.
5. Удаление файла новым коммитом **не очищает историю** и не отзывает секрет. Если требуется очистка истории, сначала согласовать остановку push с командой и подготовить отдельную очищенную копию. Публикация переписанной истории требует согласования владельца репозитория; затем участники должны использовать чистые клоны, чтобы не вернуть старую историю.

После получения коммита, удаляющего отслеживаемый `.env`, Git может убрать этот файл в других клонах. Восстановите локальную конфигурацию из `.env.example` и используйте уже заменённые секреты.

См. [инструкцию GitHub по удалению чувствительных данных](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository). Старые клоны, forks и ссылки на коммиты могут сохранять данные даже после переписывания истории. Отзыв/замена секретов остаётся обязательным шагом.

## Защита от повторного добавления .env

Проверка `node scripts/check-env.mjs` запрещает `.env` и его варианты в индексе Git; для `.env.example` разрешены только пустые значения учётных данных. Это проверка файлов окружения, а не универсальный сканер секретов и не очистка истории.

В каждом клоне с установленным Node.js подключите проверку перед коммитом:

```sh
git config --local core.hooksPath .githooks
```

Если в клоне уже настроены собственные Git hooks, добавьте вызов `node scripts/check-env.mjs` в существующий pre-commit вместо замены hooksPath. Не используйте `git add -f` для секретных файлов и не обходите проверку через `--no-verify`. Администратору репозитория следует включить GitHub secret scanning / push protection, если эти функции доступны; локальные hooks не защищают коммиты через веб-интерфейс и другие клоны без установленного hook.
