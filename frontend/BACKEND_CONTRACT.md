# Контракт для завершения P0/P1

Frontend подготовлен к следующему контракту. В проверенной версии `main` (`4328872`) `/api/cart` отсутствует, `added_to_cart` ограничен `false`, полей `cart_url` и `min_order` нет. Поэтому полноценное добавление требует перечисленных серверных изменений. Бизнес-логика backend не менялась; при интеграции удалён случайный текст `git status` после последней Python-инструкции, препятствовавший запуску.

## Корзина и сессия

- `POST /api/chat` сохраняет текущий запрос: `query`, `history`, `confirm_cart: [{product_id, quantity}]`.
- Реальное добавление выполняется только при явном `confirm_cart`, после повторной проверки остатка и кратности. Ответ `cart` содержит `status`, `items`, `added_to_cart: boolean`, `cart_url: абсолютный http(s) URL | null`.
- `GET /api/cart` возвращает `{items: [{product_id, name, quantity, price, currency, stock, url}], total, currency}`. ID — строки; количества и суммы — числа. Неизвестные цена/остаток/валюта могут быть `null`; пустая корзина — `items: []`.
- Обе операции используют одну серверную сессию через HttpOnly cookie. Cookie должна распространяться на `/api/chat` и `/api/cart` (например, `Path=/`), с подходящими для окружения `Secure`/`SameSite`. Frontend не создаёт сессию и не хранит собственную корзину.
- `total` берётся с сервера. Счётчик показывает количество позиций (`items.length`), а не сумму упаковок с разными единицами измерения.
- `/cart` уже реализована статическим `frontend/cart/index.html`. Существующий FastAPI mount обслуживает `/cart/` на одном origin. Node dev-прокси передаёт Cookie/Set-Cookie и GET `/api/cart`.
- До появления endpoint frontend показывает недоступность, а не вымышленную пустую корзину. Необходима отдельная проверка на настоящем сервере: добавление → cookie → GET корзины → reload.

## Товар

- `article`, `image`, `url` уже поддержаны. Артикул строкой сохраняет ведущие нули.
- Добавить `min_order: положительное число | null`, полученное из `KRATNOST_MIN`. Backend повторно проверяет минимальное количество и кратность при добавлении. Frontend использует поле для `min` и `step`, но не является защитой серверной операции.
- `stores: [{id, name, quantity}]` должен содержать только продаваемые склады. Frontend скрывает нулевые, отрицательные и неизвестные остатки, но не может определить тип склада без данных backend.
- Отсутствующая `unit` не препятствует выбору. UI использует обобщённое локализованное обозначение; исходные данные товара не меняются.
- Человекочитаемые характеристики приветствуются; временный frontend-фильтр скрывает перечисленные служебные коды EKT.
